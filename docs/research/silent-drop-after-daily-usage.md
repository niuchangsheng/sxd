## 处理策略

`internal/scheduler/dropbackoff.go` 提供统一的连续静默丢包退避：

- 第 1、2 次无回包：按例程原有短冷却重试（10~60 分钟）；
- 连续第 3 次：挂起至次日每日重置 **00:05**，避免整晚反复空等；
- 任何一次请求恢复回包即清零计数。

已接入：`soul_hunt`、`endless_expedition`、`wuliang_jiehai`、
`levitate_perfusion`、`era_rebirth_attr_gift`、`st_union_ritual`。

## 无量劫海章节扫描

`853/2` 的章节 id 来自客户端静态表（抓包实测 1、3、4、5、6…，2 不存在）。
例程改为扫描 1..8：无回包的章节直接跳过（4 秒超时、不做 PrevAct 重试），
只有全部章节都无回包时才计入「连续静默丢包」退避。

实测 2026-11-15 17:11：1~8 **全部**无回包，而同一条会话里 853/0、853/1
（空参数）正常返回，说明当天该账号的 853 章节面板整体不可用，不是单章问题。
扫描方式的价值在于：若只是部分章节不可用，仍能自动找到当前可用章节。

2026-11-15 17:56 重启后 `853/1` 返回值：era_level=110、mission_level=15、
rank=0、rank_perc=0、era_zone=1。账号进度已到 mission_level=15，
仍全部无回包，排除了「章节 id 超出进度范围」的可能。
