# PrevAct 链锚点：官方客户端取「最后收到的包」

日期: 2026-11-15
账号: qq s0 (s0-tongchen)
抓包: `/tmp/wuliangjiehai.pcapng`（无量劫海）、`/tmp/henduo.pcapng`（多玩法）

## 问题现象

多个玩法在一条长会话里运行一段时间后，**带参数的请求**开始持续无回包（静默丢包），
而**空参数请求**始终正常：

| 模块 | 正常（空参） | 静默丢弃（带参） |
| --- | --- | --- |
| 851 修真境界 | 851/0、851/1、851/4 | 851/5 `[item_id, num]` |
| 853 无量劫海 | 853/0、853/1 | 853/2 `[chapter]` |
| 669 灵域猎妖 | 669/1 | 669/3 `[step]` |
| 797 无尽洞天 | 797/20、797/21 | 797/32、797/22、797/23 |
| 179 仙盟上香 | 179/0、179/10 | 179/11 `[offer_id]` |
| 429 魔界远征 | 429/1、429/2 | 429/63 `[type]`（屠魔令为 0 时同样丢包） |

全新登录后立即运行同一例程可以成功（探针实测），说明包体格式本身正确。

## 抓包结论

### 1. PrevAct = 最后收到的包

`/tmp/wuliangjiehai.pcapng` 的时间线上，客户端每个请求尾部的 4 字节 PrevAct
都等于**最近一次收到的网关包 ActionID**，而不是最近发出的动作号：

| 请求 | 请求尾 PrevAct | 最近收到的包 |
| --- | --- | --- |
| 853/0 `03570001` | 0x03570001 | 登录推送 855/1 |
| 853/2 `00000001 03550001` | 0x03550001 | 853/1 回包 |
| 853/3 `... 03560001` | 0x03560001 | 854/1（推送/回包） |
| 52/0 `03550004` | 0x03550004 | 853/4 回包 |

尤其 `853/0` 的 PrevAct 是登录推送 `855/1`，该动作从未由客户端发出，
说明**服务端推送也计入链**。

`/tmp/henduo.pcapng` 中还能直接看到 `0/23` 回包作为锚点：客户端收到 `0x00000017`
回包后，下一个 `1/1` 请求的尾部 4 字节就是 `0x00000017`，说明**普通回包
同样计入链**（因此 `lastRxActionID` 不排除心跳/查询回包，与旧的 `lastAckActionID`
「排除心跳」正好相反）。

> 2026-11-21 更正：`0/23` 是 `get_buy_power_data`，并非心跳；真正的心跳是
> `0/75 (heart)`。本节关于“回包计入 PrevAct 链”的结论不受影响。

### 2. 服务端校验 PrevAct，不一致就静默丢包

空参数请求的载荷只有 PrevAct 一个字段，服务端不读取它，因此永不失败；
带参数请求会读取并校验 PrevAct，链不一致时**不回任何包**（连错误码都没有）。
这正是「发出去没有任何反应、session.Call 超时」的根因。

### 3. 旧实现用「最后发出的包」导致链漂移

旧 `Send` 用 `lastActionID`（最后发出的包）覆盖尾部 4 字节。一旦出现：

- 服务端推送（如 140019、DA0001 心跳回包、854/1）之后；
- 某次请求被静默丢弃（lastActionID 前进，服务端链不动）；
- 心跳包发出后（lastActionID=0x17，但服务端链仍是它最后发出的包）；

本地链就与服务端链错位，之后所有**带参数**请求都会持续丢包，直到重连。

## 修复

`internal/client/session.go`:

- 新增 `lastRxActionID`，在 `readLoop` 中对**每个收到的包**（含推送、心跳回包）更新；
- `Send` 覆盖尾部 PrevAct 时优先使用 `lastRxActionID`，仅当会话从未收到包时回退
  `lastActionID`；
- `CallWithPrevActResync` 的显式锚点改为**重试时刻的** `lastRxActionID`
  （期间到达的推送也要计入），不再固定用 `LastAckActionID`；
- 保留 `RecentRxActions()` 环形缓冲作为静默丢包诊断（超时日志会打印最近收包序列）。

回归测试：

- `TestSendUsesLastReceivedPushAsPrevAct`：推送到达后，下一次请求尾部必须是推送动作号；
- `TestCallWithPrevActResync`：首次丢包后用最新锚点重试成功。

## 排查提示

遇到「某模块的带参请求一直超时、空参请求正常」时，先看超时日志里的
`recent_rx`：如果最后收到的是推送/心跳回包，而请求尾部 PrevAct 是旧的业务动作，
就是链锚点问题，不是玩法协议本身的问题。
