# 15. 业务回包结果码强制解析与失败语义分流

日期: 2026-11-03

## 状态

已通过 (Accepted)

## 上下文 (Context)

部分 Routine 在发送业务请求后仅判断 `session.Call` 是否超时或是否收到同 ActionID 的回包，未解析回包中的 `result_code`。这会把“次数不足”“冷却中”“无可领悟技能”“等级/前置条件不满足”等业务失败误记为成功，并在后续定时唤醒中继续重复发包，造成日志污染、带宽浪费与额外的风控暴露风险。

同时，各模块的成功码并不统一（例如登录 `4`、竞技场 `0`、跨服登录 `2`、在线礼包 `97`），无法用单一常量判断成功。

## 架构决策 (Decision)

确立以下强制契约：

1. **禁止丢弃应答**：所有发送业务请求的代码必须持有并解析回包结果码。禁止 `_, _ = session.Call(...)` 丢弃带结果码的响应；仅心跳、纯通知或协议明确无 `result` 字段的封包可豁免，且必须在代码注释中说明协议依据。
2. **先校验结果码，再读业务数据**：失败回包可能被截断；在确认成功前禁止读取或采信后续业务字段。
3. **成功值按模块定义**：以 [protocol-spec.md](../protocol-spec.md) 的模块协议为准，严禁统一假设 `0` 为成功。
4. **失败语义驱动下一步**：
   - 次数不足 / 今日已用完 → 返回 `scheduler.ErrAttemptsExhausted`，熔断至次日重置；
   - 冷却中 → 读取 `cdTimer` / 冷却字段后退出等待，除显式配置外禁止消耗元宝清冷却；
   - 条件不满足（等级、前置任务、无可领悟技能、无可挑战目标）→ 返回 `scheduler.ErrConditionNotMet` 或本轮正常退出，禁止原样连续重试；
   - 背包已满 → 返回 `scheduler.ErrBagFull`，进入短冷却；
   - 未知错误码 → 记录 `routine`、`ActionID`、`result_code` 后终止本轮，禁止盲目重发。
5. **成功回包需校验副作用**：次数是否推进、奖励是否到账、状态是否变化；出现“成功码但业务未生效”时记录告警并按失败处理。
6. **测试强制覆盖**：新增或修改玩法必须覆盖成功路径与至少一个失败码路径；仅验证“回包到达”的测试视为无效。

## 结果与影响 (Consequences)

### 正向收益

- 消除“收到回包即成功”的假成功路径，日志与任务状态可信；
- 业务失败可触发正确的熔断/挂起，避免无谓重试与风控暴露；
- 每个模块的回包结构与结果码在实现与测试中显式沉淀。

### 潜在代价

- 新玩法需要为每个请求补充回包结构体、结果码常量与失败分支测试；
- 存量 Routine 在下一次触碰时必须优先补齐回包解析，半成品实现将不再被接受为完成状态；
- 逆向未知的回包结构需要额外的抓包/探针验证，可能延缓部分玩法上线。
